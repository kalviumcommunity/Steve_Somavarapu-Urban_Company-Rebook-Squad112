# Auth.js / NextAuth — Quick Notes

## 1. What is Auth.js?

**Auth.js (NextAuth)** helps us add authentication to a Next.js application.

It handles things like:

* Login / Logout
* OAuth
* Sessions
* Cookies
* User accounts
* Route protection

### Remember:

```text
Authentication → Who are you?
Session        → Are you still logged in?
Authorization  → What are you allowed to do?
```

---

## 2. Providers

A **Provider** is a login method.

Examples:

```text
Google
GitHub
Credentials (email + password)
```

---

## 3. OAuth

OAuth allows users to log in using another service like Google without giving our app their Google password.

```text
App → Google → Login → Callback → App
```

---

## 4. Sessions

A session remembers the logged-in user.

It can contain:

```text
id
email
name
role
```

Example:

```js
session.user.role = "admin"
```

---

## 5. JWT vs Database Sessions

### JWT

Session information is stored in a token.

**Pros:** Fast, no database lookup.

### Database Session

Session information is stored in the database.

**Pros:** Easier to revoke and control.

---

## 6. Callbacks

Callbacks allow us to customize authentication.

For example, adding a user's role to the session:

```text
Database User
     ↓
Callback
     ↓
Session
     ↓
role: "admin"
```

---

## 7. Adapters

Adapters connect Auth.js to a database.

Example:

```text
Auth.js → Prisma → PostgreSQL
```

They can store:

* Users
* Accounts
* Sessions
* Verification tokens

---

## 8. Route Protection

We can protect pages such as:

```text
/dashboard
/admin
```

Example:

```text
User visits /dashboard
        ↓
Logged in?
   ↓       ↓
  Yes      No
   ↓       ↓
Dashboard Login
```

But protecting the page isn't enough.

**Server actions/API routes must also check permissions.**

---

## 9. RBAC

RBAC = **Role-Based Access Control**

Example:

```text
student → basic features
mentor  → mentor features
admin   → admin features
```

The server should check the role before performing sensitive actions.

```text
Request
   ↓
Authenticated?
   ↓
Correct role?
   ↓
Allow / Reject
```

---

## 10. Secrets

Never expose secrets in frontend code.

Keep things like:

```env
AUTH_SECRET=
GOOGLE_CLIENT_SECRET=
DATABASE_URL=
```

inside environment variables.

---

## 11. Most Important Rule

### Authentication ≠ Authorization

Being logged in doesn't mean you can do everything.

```text
Authentication
     ↓
Who are you?

Authorization
     ↓
What can you do?
```

### Example

An admin dashboard should have **3 checks**:

```text
1. User is logged in
        ↓
2. User has admin role
        ↓
3. Server checks admin role again
        ↓
   Allow action
```

> **Authentication tells you who the user is. Authorization tells you what they're allowed to do.**
